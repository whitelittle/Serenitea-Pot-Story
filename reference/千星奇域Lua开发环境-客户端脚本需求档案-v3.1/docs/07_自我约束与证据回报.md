# 自我约束与证据回报

这是一页交付准则。它让 AI 和人类作者都能说明“查了什么、写了什么、还不知道什么”，不要求新手在创建每个控件后立即进行真机验证。

## 1. 先完成四项自检

### API

- 所有宿主 API 都回查 [`客户端控件API文档.md`](./客户端控件API文档.md)；
- 标识、点号/冒号、参数、返回值、字段读写性、枚举和生命周期没有猜测；
- 找不到完整定义的能力标为 `unknown`，不靠试玩猜 API。

### 对象与编号

- 容器节点索引、控件模板索引 `prefabIndex`、运行时 `id`、图片 `imageId`、脚本映射 `scriptMappingId` 分开命名；
- 已确认父级作用域：同一个模板索引可能在不同父控件下重复；
- 模板子节点和已挂载画布节点是否可以动态创建，按官方指南和 API 规则判断，不把所有节点都当成可实例化模板。

### 生命周期与资源

- 创建成功的控件、监听器、Tween 都有拥有者；
- 禁用、故障和销毁时能停止 Tween、注销监听、清空引用；
- 新 Tween 开始前不会与旧 Tween 同时写同一对象同一字段；
- 纯 Tween 表现不为了“保险”强行打开逐帧。

### 可读性

- 配置集中在顶部，明确约定的 ID 占位会安全拒绝；零位置/角度等合法数值照字段定义处理；
- 模板注释解释“填什么、为什么、何时删掉”；
- 代码分成小函数，回复用人能复查的中文描述，避免只丢一大段框架。

## 2. 证据和真机状态分开

每个关键结论分别写两列：

| 字段 | 可用值 | 说明 |
|---|---|---|
| `evidence_source` | `documented` | 当前包内 API/官方指南明确写出 |
|  | `static_checked` | Lua 语法、标识、参数和生命周期已完成静态核对；不等于运行通过 |
|  | `provided_unverified` | 创作者、样本脚本或资产清单提供，尚未确认 |
|  | `user_confirmed` | 用户确认既有工程运行结果，注明工程范围 |
|  | `video_observed` | 画面出现过，仅证明该视频中的显示内容 |
|  | `inferred` | 从文档和代码静态推导 |
|  | `observed` | 在目标编辑器或游戏运行时直接观察 |
|  | `unknown` | 证据不足或互相冲突 |
| `device_status` | `passed` / `failed` | 已做运行观察并记录结果 |
|  | `confirmed_by_user` | 用户确认原工程运行，可采用且不要求重复证明 |
|  | `pending` | 需要观察但尚未执行 |
|  | `not_required` | 文档事实或静态规则，不需要真机 |
|  | `unknown` | 连所需观察条件也不明确；处理方式见 [05 知识层级验证与 Debug](05_知识层级验证与Debug.md) §1 |

示例：API 文档写明 `Tween:Kill(false)`，可写 `documented + not_required`；编辑器中提供了一个图片数字但未运行，可写 `provided_unverified + pending`。不能把前者写成“实机通过”，也不能把后者的数字当作包内事实。

## 3. unknown 的处理

发现 `unknown` 时：

1. 指出缺失的是 API 定义、控件索引、父级作用域、图片资产还是运行时行为；
2. 暂停依赖该事实的那一小段，不要让整份需求停摆；
3. 给出最小补充信息，例如一个完整 API 小节、一个编辑器属性值或一个父控件路径；
4. 其他已有依据的代码继续做静态实现。

不要用“应该”“一般来说”“试玩看看就知道”代替证据，也不要把 `pending` 当失败。

## 4. 回复模板

交付代码或方案时使用下面的短格式：

```text
完成内容：<文件/函数/表现>
API 依据：<docs/客户端控件API文档.md 的章节>
静态检查：通过 / 有问题（说明问题）
证据：<documented | provided_unverified | user_confirmed | video_observed | inferred | observed | unknown>
真机状态：<passed | failed | confirmed_by_user | pending | not_required>
未决事项：<没有则写“无”；unknown 列出最小补充信息>
运行前动作：<需要建立哪些脚本映射、挂载哪个入口；不把它写成编码前置条件>
```

## 5. 交付前一页清单

- [ ] 入口文件和模块职责清楚；
- [ ] `require` 路径的证据状态写明。官方使用指南只确认脚本映射和上传规则，并提到 `scriptMappingId` 可用于跨脚本调用；原 OOO 的模块用法只是可选外部参考，可记 `user_confirmed` 的工程范围；新目录/映射方式尚无依据时保留 `pending/unknown`，不能伪造“官方通用支持”；
- [ ] `prefabIndex`、运行时 `id`、图片 `imageId` 没有混用；
- [ ] API 标识逐项回查，未命中为零；
- [ ] 配置缺失会安全拒绝；
- [ ] 错误不会被空 `pcall` 吞掉，故障有清晰日志；
- [ ] Tween、监听和动态控件有清理；
- [ ] 日志不逐帧刷屏，故障块只输出一次；
- [ ] 不把静态完成说成真机通过；
- [ ] 创作者无需先完成真机验证才能拿到代码和手写步骤。

更具体的 API 查阅、图片资产和 Debug 规则分别见 [`01_API阅读与防混淆.md`](./01_API阅读与防混淆.md)、[`02_图片资产ID索引.md`](./02_图片资产ID索引.md)、[`05_知识层级验证与Debug.md`](./05_知识层级验证与Debug.md)。
