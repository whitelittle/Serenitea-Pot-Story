# 知识层级、验证与 Debug

这份文档给 AI 和新手作者一套可复查的自我约束。它把“文档写了什么”“代码推断了什么”“运行时看到了什么”分开记录，因此创建控件后不需要被强制要求立即真机验证。

## 1. 知识层级代码

在设计记录、注释或回复中给每个关键结论标一个 `K` 类别。编号用来区分证据来源和检查程度，不表示“数字越大就更权威”。API 定义始终以当前官方文档为准；静态检查和样本不能升级成真实观察。

| 代码 | 名称 | 可以说明什么 | 不能说明什么 |
|---|---|---|---|
| `K0` | unknown | 资料不足、冲突或无法定位 | 不能写进依赖该事实的实现 |
| `K1` | documented | 在包内 API 文档或官方指南中明确写出 | 不能证明当前工程已挂载或运行成功 |
| `K2` | static_checked | Lua 语法、字段名、参数和生命周期通过静态核对 | 不能证明客户端运行时行为 |
| `K3` | provided（细分见下文） | 创作者或样本提供的写法、数据和运行报告 | 不自动覆盖改写后的目标工程 |
| `K4` | observed | 在目标编辑器或游戏运行环境直接观察到 | 只覆盖当时版本、对象和配置，不能替代文档 |
| `K5`（别名 `I`） | inferred | 从文档、代码结构或样本推导出的工程判断 | 不是文档声明，也不是运行观察，不能升级为真机通过 |

视频画面单独标 `video_observed`，只证明画面中的内容，不等于本次目标客户端的 K4。

K3 细分：`provided_unverified` 表示只收到资料而未确认；`user_confirmed` 表示用户明确确认运行或使用结果。记录确认人/时间/工程范围即可采用，不要求用户重复验证。`REF-OOO` 只作为可选外部结构参考，不在本包记录其运行状态；新模板的结果另列。

`K0–K5` 是证据等级；`evidence_source` 和 `device_status` 是交付时的两个记录字段。不要把 `K3`、`user_confirmed`、`pending` 当成同一列互相替换，具体回报格式以 [自我约束与证据回报](07_自我约束与证据回报.md) 为准。

每条结论再单独填真机状态：

- `passed` / `failed`：本次已直接观察并记录结果；
- `confirmed_by_user`：用户确认的既有运行结果，注明原工程范围；
- `pending`：需要观察但尚未做；
- `not_required`：该结论是文档或静态约束，不要求真机；
- `unknown`：连所需观察条件也不明确。

示例：

```text
结论: TweenSequence:Join 与队尾步骤并行
证据: K1 / documented
真机状态: not_required

结论: CardArt 使用 imageId=123456 显示
证据: K3 / provided_unverified（编辑器属性截图）
真机状态: pending
```

## 2. 可验证代码标记

复杂脚本在配置区保留一份简短的自检信息，帮助读者知道哪些值必须替换：

```lua
local CONFIG = {
    CARD_PREFAB_INDEX = 0,     -- K3: 控件模板索引；不要填运行时 id
    IMAGE_ID = 0,              -- K3: 图片资产 id；不要填 prefabIndex
    DEBUG = true,
}

local KNOWLEDGE = {
    api_source = "docs/客户端控件API文档.md", -- K1
    static_checked = false, -- 完成逐项回查后改为 true
    runtime_observed = false, -- 只有真实观察后才改为 true
}
```

规则：

1. 配置中明确约定的 ID 占位 `0`、`nil`、空字符串表示未配置；不能当真实 ID。位置、角度、透明度和枚举中的零是否有效，分别按字段定义判断，不能一律拒绝。
2. 注释中的 `K1–K5` 必须对应实际证据；`K` 编号不是权威排序，不能为了让代码看起来完整而写 `K4` 或 `K5`。
3. `static_checked` 和 `runtime_observed` 是作者的记录开关，不是引擎 API，也不能替代日志。
4. 任何 `K0` 结论都不能成为必经路径；将功能关掉或等待资料，不用试玩猜答案。

## 3. 五步验证链

### L0：Lua 结构

检查括号、`end`、局部变量、表结构、字符串和函数返回路径。优先保持模板短小，每次只加一个能力。没有必要时不引入复杂模块或逐帧循环。

### L1：API 事实

按 [`01_API阅读与防混淆.md`](./01_API阅读与防混淆.md) 的步骤逐项核对宿主 API：精确标识、点号/冒号、参数、返回值、读写性、可补间字段、枚举和生命周期。未命中必须为零。

### L2：结构与所有权

不运行游戏也能检查：

- 脚本确实有启动入口和销毁入口；
- 容器节点索引、控件模板索引、运行时 id、图片 id 使用了不同变量名；容器节点索引只用于挂载，控件模板索引只表示模板身份，查找时要保留父级作用域；
- 只有文档允许的存为模板父节点可动态创建；画布节点和模板子节点不能仅凭索引实例化；
- 动态控件、监听器和 Tween 创建成功后立即登记拥有者；
- 同一对象同一字段不会被多条 Tween 同时写；
- 关闭/销毁时停止 Tween、注销监听并清空引用；
- 配置缺失会产生明确错误，而不是调用 `nil` 或 `0`。

可选模拟检查：用受控的宿主替身检查容量、重复触发、取消、监听与清理，记录替身假设及结果。它证明的是这些假设下的 Lua 逻辑，不证明引擎行为；不能标为 K4。

### L3：日志和最小探针

仅当 API 文档已经声明、但当前对象状态不清楚时，才加一个临时探针，例如打印 `typeof`、`alive`、`prefabIndex` 或文档声明的方法返回值。探针必须：

- 只读，不修改玩法状态；
- 用 `pcall` 包住已知 API；
- 有唯一前缀和开关；
- 记录完就删除或关闭。

### L4：可选运行观察

只有以下情况才建议创作者试玩或查看日志：创作者主动要求确认画面，或某个关键行为在文档中明确为运行时条件。最小观察只验证一个假设，例如“目标控件是否存活”或“这一条 Tween 是否播放”，不把整套玩法交给创作者校准。

## 4. Debug 顺序

出现“没显示、没动、报错”时按顺序查，每一步都有明确停止条件：

1. **加载**：文件顶部一次性 `print`，确认脚本映射确实加载。
2. **挂载**：记录 `script.path`、`script.object` 和对象 `alive`；按当前例子的宿主类型检查挂载，不把“容器节点”当所有脚本的唯一宿主。
3. **容器**：确认容器和父级的 `active`、`visible` 状态；隐藏、未激活和脚本停止是不同现象。
4. **实例**：按文档声明的 `prefabIndex` 或名称取得子控件；不要拿口头“ID”猜查找函数。
5. **字段**：读取并记录目标字段的当前值，确认字段可写且是 Tweenable；先用一个静态赋值排除动画时间线问题。
6. **动画**：确认对象 `alive`、起点和目标值、绝对/相对模式、缓动和持续时间；同字段新动画先停止旧动画。
7. **清理**：检查 `OnDisable`/`OnDestroy` 是否停止动画和注销监听，避免旧回调改写已销毁对象。
8. **证据**：把日志、代码版本、配置和 `K` 级别一起记录，不能只报“看起来没反应”。

## 5. 日志规则

- 普通阶段和一次性状态走 `print`，错误走 `printerr`。
- 每条带脚本或模块前缀；同一消息用 `seen` 去重。
- 逐帧日志只允许启动前几帧或低频心跳；Tween 表现本身不需要逐帧打印。
- 致命故障输出一个连续块：

```text
GAME FAULT BEGIN <错误码>
  phase: <阶段>
  message: <原因>
  object: <对象或 nil>
  evidence: <K级别/来源>
  traceback: <调用栈文本；取不到写“不可用”>
  cleanup[1..n]: <清理错误，只追加，不覆盖首个错误>
GAME FAULT END <错误码>
```

后续帧不要重复同一故障块。清理失败追加到原故障信息，不覆盖首个错误。

## 6. 常见混淆的处理

| 现象 | 先做什么 |
|---|---|
| `prefabId` 和 `prefabIndex` 都出现 | 回查 7.1 API；文档未声明的标识降为 `K0`，不要兼容猜测 |
| 容器节点索引与模板索引数值相同 | 保留角色名和父级作用域；确认节点是否为文档允许动态创建的模板父节点 |
| 图片能找到但显示不对 | 分开核对 `imageSource`、`imageId`、控件类型和 `active/visible` |
| Tween 创建成功但不动 | 依次核对字段是否 Tweenable、对象是否 alive、容器是否激活、是否有旧 Tween 抢写 |
| `OnUpdate` 没日志 | 确认是否显式开启逐帧；纯 Tween 逻辑不要为了计时强行开启 |
| 试玩后才知道某 API 不存在 | 这是流程错误；先回查 API 文档，不能把试玩当 API 搜索器 |

## 7. 回复与交付格式

完成静态实现时，回复至少包含：

```text
已核对 API: <文件路径/章节>
静态检查: K2 / 通过或列出问题
运行观察: K4 / passed；用户确认用 K3 / confirmed_by_user 并注明原工程；其他用 not_required 或 pending
已知 unknown: <没有则写“无”>
Debug 入口: <日志前缀、开关、探针位置>
```

“代码已写好”不等于“真机通过”。如果没有运行观察，明确写 `not_required` 或 `pending`，不要要求新手为了完成控件创建而先做真机验证。
